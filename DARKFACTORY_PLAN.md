# План разработки Darkfactory

Статус: требования согласованы по итогам интервью; технический выбор исполнительных компонентов подтверждается на этапе 1. Дата: 20 октября 2026 года.

## Цель

Создать отдельный проект Darkfactory: приватную фабрику разработки для нескольких организаций и проектов, размещаемую на инфраструктуре владельца. Первый подключаемый проект — nocode-x. Реализация фабрики должна находиться в отдельном репозитории. Публичный SaaS не является целью первой версии.

Фабрика принимает два типа запросов:

- Сообщения пользователей об ошибках: воспроизведение, исправление и проверка.
- Задачи владельцев: уточнение требований, планирование, разработка и проверка.

Запросы поступают через интерфейс фабрики и API. После постановки задачи фабрика самостоятельно проходит планирование, разработку, проверки, независимое ревью и слияние в интеграционную ветку `preprod`. К человеку обращается при нехватке данных или доступа и после исчерпания установленных лимитов.

Результат первой версии — проверенное изменение в `preprod` с доказательствами выполнения критериев готовности. Для Git-хостингов с поддерживаемой интеграцией создаётся PR/MR; для обычного Git доказательства и история изменения хранятся внутри фабрики. Если обязательные проверки проекта не настроены, фабрика только готовит PR/MR или внутреннюю запись изменения для человека и не выполняет автослияние.

Перенос в основную ветку и production выполняет человек. `preprod` в первой версии — ветка с проверками, без автоматического развёртывания приложения. Автоматическое развёртывание в production также не входит в первую версию.

## Основные решения

- Одна фабрика обслуживает несколько организаций. В каждой организации может быть несколько проектов.
- Организация владеет своими подключениями, секретами, участниками и ограничениями.
- Проект определяет репозитории, инструкции, окружение, команды проверок и правила приёмки.
- Поддерживаются GitHub, GitLab, их корпоративные установки, другие Git-серверы и локальные репозитории. Работа с Git отделена от интеграции с PR/MR конкретного хостинга.
- Доступ к интерфейсу и API ограничивается организациями и проектами. Предусмотрены роли владельца, оператора и наблюдателя.
- Роль агента отделена от исполнителя: разработчика или ревьюера можно назначить на разные агентные среды.
- Начальная схема: Codex разрабатывает, Claude выполняет ревью. Исполнители и приоритеты настраиваются для проекта; при недоступности одного движка роль может выполнять другой.
- Подписочные Codex и Claude Code подключаются как готовые агентные среды. Для OpenAI-совместимых моделей используется отдельный агентный движок.
- Организация может объединять подписочные аккаунты в пулы. При исчерпании квоты фабрика автоматически выбирает другое доступное подключение по заданной политике.
- Автоматический переход Codex ↔ Claude включён с первой версии. Платный API автоматически не подключается по умолчанию; явное назначение API-агента задаче разрешено.
- Фабрика управляет задачами и передачей работы между исполнителями. Наличие вложенных подагентов у конкретного исполнителя не является обязательным условием.
- Задачи поддерживают зависимости, подзадачи, ссылки на дубли и связи с другими задачами. Зависимости определяют порядок запуска.
- Каждая задача выполняется в отдельном контейнере и рабочей ветке, с тестовым окружением и явно разрешёнными подключениями. Агент не получает доступ к хосту и production-секретам.
- Результаты проверок привязаны к конкретному коммиту. Изменение коммита требует повторной проверки.
- Автослияние в `preprod` требует обязательных проверок проекта на результате объединения с текущей целевой веткой и независимого ревью в отдельной сессии.
- Пределы пилота: две одновременно работающие задачи на всю фабрику, 60 минут активной работы на задачу и три цикла исправления. Пределы настраиваются и не обнуляются при смене исполнителя или перезапуске.
- Используем готовые исполнительные компоненты там, где они подходят. Решение об их выборе принимаем после проверки адаптеров.

## Структура

```text
Фабрика
├── Организация A
│   ├── Участники и права
│   ├── Подключения аккаунтов и API
│   ├── Пулы подписочных аккаунтов и правила переключения
│   ├── Общие роли агентов и ограничения
│   ├── Проект nocode-x
│   │   ├── Репозитории и инструкции
│   │   ├── Окружения и проверки
│   │   └── Задачи и запуски
│   └── Другой проект
└── Организация B
    └── Собственные подключения, проекты и задачи
```

## Репозитории и Git-хостинги

- Подключение репозитория содержит адрес или разрешённый локальный путь, способ авторизации, ссылку на секреты и настройки основной и интеграционной веток. Интеграционная ветка по умолчанию — `preprod`.
- Git-операции поддерживают удалённые серверы и локальные репозитории. Координатор получает доступ только к разрешённому локальному репозиторию; агент работает с отдельной копией внутри контейнера, без доступа к остальной файловой системе хоста.
- Адрес GitHub или GitLab настраивается: интеграции не ограничиваются публичными доменами. Корпоративные установки используют собственные подключения и авторизацию.
- Провайдерные адаптеры создают и обновляют PR/MR там, где такая интеграция поддерживается. Отсутствие адаптера PR/MR у другого Git-хостинга не запрещает обычную работу с Git.
- Для обычного Git и локальных репозиториев фабрика хранит внутреннюю запись изменения: исходный запрос, ветку, diff, коммиты, заключение ревьюера и результаты проверок. После приёмки изменение сливается в `preprod` по тем же правилам.
- Повторы и восстановление после сбоя не создают дубли рабочих веток, PR/MR, внутренних записей изменения или уже выполненных слияний.

## Этап 1. Проверить три типа исполнителей

Цель — подтвердить возможность управлять нужными исполнителями через единый интерфейс до разработки остальной платформы.

| Адаптер | Способ работы |
|---|---|
| Codex | Подписочный аккаунт, программное управление через App Server |
| Claude Code | Подписочный аккаунт, неинтерактивный CLI и события `stream-json` |
| API Agent | Агентный движок с выбранным OpenAI-совместимым endpoint |

Общий контракт адаптера должен поддерживать:

- Запуск задачи в заданном рабочем каталоге внутри изолированного контейнера.
- Получение статуса, событий и результата.
- Отмену запуска.
- Сведения о доступных возможностях исполнителя.
- Продолжение сессии, если исполнитель его поддерживает.
- Различение ошибок авторизации, исчерпания лимита и сбоя выполнения.
- Выбор конкретного подключения для запуска и изоляцию его авторизации от других подключений.
- Доступные сведения о квоте, времени её сброса и возможности повтора. Если исполнитель их не сообщает, состояние фиксируется как неизвестное.

Одинаковый контракт не означает одинаковую поддержку всех возможностей. Ограничения каждого адаптера фиксируются явно.

Для Codex отдельно проверить допустимый способ авторизации для выбранного размещения фабрики. По документации OpenAI встроенная авторизация App Server не разрешена для коммерческих или размещённых сервисов; для них предусмотрен Sign in with ChatGPT. Доступность этой интеграции необходимо подтвердить до выбора схемы подключения.

**Критерии готовности:** каждый адаптер внутри контейнера изменяет тестовый репозиторий, запускает проверку и возвращает diff. Проверены отмена, ошибка авторизации, исчерпание лимита и запуск с двумя разными подписочными подключениями без смешения авторизации. Подтверждена передача незавершённой работы Codex ↔ Claude через артефакты. Зафиксированы ограничения подписочных запусков, авторизации для выбранного размещения и варианты продолжения сессии. Отсутствует доступ к хосту и production-секретам.

## Этап 2. Собрать ядро фабрики

Начальная архитектура: один сервис управления, PostgreSQL и отдельные процессы исполнителей в изолированных контейнерах. Очередь задач первоначально хранится в PostgreSQL. Минимальный API создания задач, чтения состояния и управления задачами входит в ядро; API и интерфейс используют общий конвейер и правила доступа.

| Сущность | Назначение |
|---|---|
| Организация | Участники, подключения и общие ограничения |
| Участник и доступ | Роль человека и разрешённые организации и проекты |
| API-токен | Пользователь, ограниченные права и область доступа токена |
| Проект | Репозитории, инструкции, окружения и команды проверок |
| Репозиторий | Git-адрес или разрешённый локальный путь, подключение, ветки и возможности PR/MR |
| Подключение | Подписочный аккаунт, API endpoint или Git-подключение, ссылка на секреты и состояние доступности |
| Пул подписок | Подключения одной организации, приоритеты, совместимость и правила автоматического переключения |
| Резервирование подключения | Запуск, занятый слот аккаунта, срок аренды и подтверждение активности исполнителя |
| Состояние квоты | Подключение, известные лимиты и время сброса, источник и время обновления сведений |
| Роль агента | Инструкции, разрешённые инструменты и выбор исполнителя |
| Задача | Исходный запрос, критерии готовности и состояние |
| Связь задач | Тип связи, исходная и целевая задачи; зависимости управляют допуском к запуску |
| Запуск | Исполнитель, сессия, события и результат попытки |
| Проверка | Коммит, команды, результаты и замечания |
| Изменение | Рабочая ветка, PR/MR или внутренняя запись, проверенный результат и состояние слияния |
| Инцидент интеграции | Поломка `preprod`, затронутые задачи, диагностика и состояние ограниченного исправления |

При перезапуске фабрика должна восстанавливать состояние задач и учитывать уже запущенную работу. Сохраняются счётчики времени и исправлений, блокировки интеграции и состояние инцидентов. Повторная доставка задания не должна создавать дубли веток, PR/MR, внутренних записей изменения или слияний.

Выбор подключения и резервирование слота выполняются атомарно. После перезапуска истечение аренды само по себе не разрешает второй запуск: сначала требуется остановить прежнего исполнителя или подтвердить его завершение.

### Связи между задачами

| Тип связи | Поведение |
|---|---|
| Зависит от | Задача ждёт принятый результат задачи-предшественника |
| Подзадача | Задача входит в родительскую; обязательные подзадачи участвуют в приёмке родителя |
| Дубль | Задача ссылается на основную; отдельная работа по дублю прекращается после подтверждения связи |
| Связана с | Информационная связь без изменения порядка выполнения |

- Связи доступны только между задачами одной организации. Между проектами связи допустимы при наличии прав на обе задачи.
- У подзадачи один родитель. Циклы и ссылки задачи на саму себя запрещены в иерархии и зависимостях. Проверяется также общий граф ожидания родительских и зависимых задач.
- Для зависимости указывается ожидаемый результат: принятые артефакты на конкретном коммите либо проверенное изменение в `preprod`, если работа требует кода предшественника. Само открытие PR/MR или подготовка внутренней записи изменения не снимает кодовую зависимость. Слияние проверенного результата в `preprod` позволяет продолжить цепочку без ручного переноса в основную ветку.
- Готовые независимые задачи могут выполняться параллельно в пределах общих ограничений. Заблокированная задача не занимает исполнителя или подписочный слот.
- Сбой или отмена предшественника сохраняет зависимую задачу в состоянии блокировки с понятной причиной. Дальнейшее действие задаётся политикой или решением человека.
- Изменение принятого результата предшественника требует повторной оценки зависимых задач и затронутых проверок. Родитель принимается только после обязательных подзадач и общей проверки результата.

### Пределы выполнения

- Начальные пределы пилота: максимум две одновременно работающие задачи суммарно по всем организациям и проектам; до 60 минут активной работы на задачу; до трёх циклов исправления. Настройки могут изменяться явно, с соблюдением ограничений организации, проекта и подключений.
- Активное время суммируется по попыткам и этапам работы задачи, включая смену аккаунта или движка. Ожидание квот, свободного слота, зависимостей или ответа человека не учитывается. При переходе в ожидание исполнитель освобождает слот после подтверждённой остановки.
- Цикл исправления — возврат разработчику после неуспешной проверки или замечаний ревьюера с повторной проверкой результата. Первичная разработка не считается циклом исправления. Смена аккаунта, движка или внутренней сессии не начинает отсчёт заново.
- Пределы действуют также при исправлении поломок `preprod`. Повторный сбой того же исправления продолжает существующий инцидент и не обнуляет счётчики.
- После исчерпания времени или трёх неудачных циклов фабрика останавливает работу, сохраняет изменения, диагностику и артефакты и ждёт решения человека. Сброс квоты или перезапуск сервиса не возобновляет такую задачу автоматически.
- Ожидающие и отменённые задачи не занимают активные слоты. Общий предел задач не заменяет отдельные ограничения аккаунтов и резервирование подключений. Исправление `preprod` также соблюдает общие пределы.

**Критерии готовности:** задача, связи, резервирования, счётчики и блокировки интеграции переживают перезапуск сервиса. Организация получает доступ только к своим данным и подключениям. Зависимые задачи запускаются только после выполнения условий; циклы и повторное занятие слота отклоняются. API соблюдает те же права и пределы, что интерфейс.

## Этап 3. Провести одну задачу до проверенного слияния в preprod

Начать с одного проекта и последовательного выполнения. Обеспечить минимальную постановку задачи через интерфейс и API, не дожидаясь полного интерфейса этапа 6.

```text
Запрос
→ уточнение критериев готовности
→ план
→ разработка в отдельном контейнере и ветке
→ тесты
→ независимое ревью
→ исправления при необходимости
→ PR/MR или внутренняя запись изменения
→ подготовка объединения с текущей preprod
→ обязательные проверки и независимое ревью итогового коммита
→ автоматическое слияние в preprod
```

План не требует отдельного утверждения человеком перед разработкой. Уточнения запрашиваются, если без них невозможно определить корректный результат.

Предусмотреть явные состояния ожидания:

- Требуется ответ человека.
- Требуется восстановить авторизацию.
- Исчерпана квота подключения.
- Нет доступного подключения в пуле.
- Не выполнена зависимость или обязательная подзадача.
- Необходимо устранить сбой окружения или исполнителя.
- Исчерпано активное время или допустимое число циклов исправления.
- Интеграция заблокирована на время исправления `preprod`.
- Не настроены обязательные проверки, требуется ручная приёмка подготовленного изменения.

Приёмка относится к конкретному коммиту. После исправлений выполняются соответствующие проверки нового коммита.

### Допуск к автослиянию

- Проект явно задаёт обязательные команды проверок и критерии приёмки. При отсутствии таких проверок фабрика доходит только до PR/MR или внутренней записи изменения, без автослияния.
- Успешных тестов рабочей ветки недостаточно: обязательные проверки выполняются на результате объединения с текущей `preprod`. Ревьюер получает исходную задачу, критерии готовности, итоговый diff и результаты проверок в отдельной сессии.
- Слияния в одну целевую ветку выполняются последовательно. Если вершина `preprod` изменилась до слияния, результат объединения пересобирается. Новый коммит требует повторных проверок и ревью; устаревший допуск не переносится на него автоматически.
- История изменения связывает проверенный итоговый коммит, результаты проверок, ревью и факт слияния. Основная ветка не является целью автоматической интеграции.

### Поломка preprod после слияния

- Фабрика фиксирует инцидент, сохраняет диагностику и самостоятельно готовит исправление в отдельной рабочей ветке, с обязательными проверками и независимым ревью.
- На время инцидента блокируются остальные слияния в затронутую `preprod` и запуск задач, зависящих от сломанного результата. Независимые задачи могут продолжать подготовку в пределах общих ограничений; их слияния в эту ветку ожидают восстановления.
- Исправление получает приоритет в очереди. Только проверенное исправление инцидента допускается к слиянию в заблокированную ветку. Другие проекты с исправной интеграционной веткой продолжают работать.
- После успешного исправления и проверок `preprod` фабрика снимает блокировку и повторно оценивает затронутые зависимости. Повторная поломка того же исправления не создаёт новый бюджет попыток.
- После трёх неудачных циклов либо исчерпания активного времени инцидент ждёт решения человека. Автоматический откат не является выбранной стратегией первой версии.

При автоматической смене подписочного подключения или движка Codex ↔ Claude фабрика сохраняет изменения, артефакты и состояние задачи, завершает прежний запуск и создаёт новую попытку. Одновременно изменять рабочий каталог может только один исполнитель. Перенос внутренней сессии между аккаунтами и движками не предполагается: новому запуску передаются задача, план, diff, результаты проверок и оставшаяся работа. Счётчики времени и исправлений сохраняются.

**Критерии готовности:** небольшой баг проходит маршрут от интерфейса или API до проверенного слияния в `preprod`. После сбоя или смены аккаунта либо движка задача продолжается без дублирования ветки, PR/MR или слияния. Проверена цепочка из двух зависимых задач, где вторая получает код первой из `preprod`. Подтверждены оба варианта: внешний PR/MR и внутренняя запись обычного Git. Без настроенных проверок автослияние запрещено. Проверены изменение вершины целевой ветки перед слиянием, ограниченное исправление поломки `preprod` и блокировка зависимостей. В результате доступны diff, итоговый коммит, тесты и заключение ревьюера.

## Этап 4. Добавить роли и подагентов

| Роль | Ответственность |
|---|---|
| Диспетчер | Выбирает проект, маршрут выполнения, приоритет и бюджет |
| Разборщик | Воспроизводит ошибку, собирает доказательства и проверяет дубли |
| Планировщик | Формулирует критерии готовности, зависимости и подзадачи |
| Разработчик | Изменяет код и устраняет замечания |
| Тестировщик | Запускает проверки и проверяет пользовательский сценарий |
| Ревьюер | Независимо оценивает изменение на конкретном коммите |
| Интегратор | Готовит PR/MR или внутреннее изменение, проверяет объединение и сливает принятый коммит в preprod |

Не каждая задача требует всех ролей. Для простого исправления достаточно исполнителя и независимой проверки. Специализацию разработчиков по backend, frontend и инфраструктуре добавлять по потребности.

Правила координации:

- Выбор исполнителя для роли настраивается в организации или проекте и может уточняться для задачи.
- По умолчанию Codex разрабатывает, Claude выполняет ревью. При недоступности предпочтительного исполнителя допускается автоматическая замена Codex ↔ Claude с учётом возможностей и разрешённых подключений.
- Подзадача получает цель, входные данные и критерии результата.
- Подзадачи и их зависимости оформляются связями задач в ядре, чтобы диспетчер учитывал их при запуске и приёмке.
- Ревьюер работает в отдельной сессии и получает задачу, критерии приёмки, diff и результаты проверок. Движок может совпадать с движком автора; самопроверка автора отдельное ревью не заменяет.
- Время, число повторов и параллельность ограничены общими правилами ядра. Передача работы между ролями не обнуляет счётчики задачи.
- Передача между исполнителями сохраняет описание задачи и артефакты. Перенос внутренней сессии между разными исполнителями не предполагается.
- Сначала отлаживается последовательная передача работы. Затем добавляются параллельные независимые подзадачи и интеграция их изменений.

**Критерии готовности:** одну задачу выполняют разные исполнители. Провал проверки возвращает работу разработчику. Параллельные подзадачи не изменяют общий рабочий каталог.

## Этап 5. Подключить несколько организаций и проектов

Дополнение по управлению агентами: профили ролей, инструкции, модель, скиллы и MCP настраиваются для проекта и могут уточняться для задачи. Интерфейс предлагает готовые роли, скиллы и MCP из списков; произвольная конфигурация остаётся в расширенных формах. Проектный агент может поставить задачу аналитику и разработчику, связав разработку зависимостью от принятого анализа. Вложенное делегирование ограничивается глубиной и количеством задач; бюджет всего дерева остаётся общим.

Довести заложенную в ядре изоляцию до рабочего уровня:

- Раздельные секреты, окружения и права организаций.
- Доступ участников и API-токенов к конкретным организациям и проектам.
- Настройки каждого проекта: репозитории, инструкции, запуск приложения, тесты и приёмка.
- Общая очередь с ограничениями по организации и подключению.
- Учёт квоты подписочного аккаунта среди всех проектов, использующих это подключение.
- Пулы подписочных подключений организации с разрешениями на использование в конкретных проектах и ролях.
- Настраиваемые приоритеты исполнителей для ролей; автоматический переход Codex ↔ Claude включён по умолчанию.
- Переход на платный API по умолчанию выключен и требует отдельного разрешения с денежным лимитом. Явное назначение API-агента не включает автоматический платный резерв для других задач.

### Участники и API

| Роль человека | Права |
|---|---|
| Владелец | Управляет доступами, подключениями и настройками своей области |
| Оператор | Ставит задачи и управляет их выполнением в разрешённых проектах |
| Наблюдатель | Читает доступные задачи, состояния и результаты |

Роли людей не совпадают с ролями агентов. Права ограничиваются организациями и проектами. API-токен принадлежит пользователю, имеет явно ограниченные права и область действия и не может получать больше прав, чем владелец токена. Проверки доступа применяются к созданию и управлению задачами, чтению результатов, подключениям и связям между проектами. Изменение прав пользователя не должно оставлять его токену прежний более широкий доступ.

Несколько проектов не получают независимые квоты только потому, что используют одно подключение. При исчерпании лимита задача ожидает либо переключается согласно заранее заданной политике.

### Пул подписок и автоматическое переключение

Под подпиской здесь понимается подключённый подписочный аккаунт. Автосмена означает выбор другого аккаунта для следующей попытки, а не покупку или изменение тарифного плана.

Подключение аккаунтов выполняется через авторизацию по ссылке и коду: Codex — device flow, Claude — ссылка и подтверждение в форме. Пул выбирается до входа. Сессия входа ограничена по времени, поддерживает продолжение и отмену; секреты вводятся только в формах подключений. Перед назначением учитываются известный остаток квоты, время наблюдения и резерв пула. Проверка снижает вероятность остановки, но не гарантирует квоту на всю задачу; сохранение кода и переключение остаются обязательными.

- Пул содержит только явно подключённые и разрешённые организацией аккаунты. Он не объединяет квоты и не изменяет ограничения провайдера.
- Для пула задаются порядок выбора, допустимые исполнители и модели, предел параллельных запусков, число переключений и задержки повторов. Автоматический переход между Codex и Claude включён с первой версии; настройки проекта определяют приоритеты и совместимость подключений с ролями.
- Лимиты и занятость учитываются по аккаунту, даже если подключение входит в несколько пулов. Подключения одного аккаунта не должны давать дополнительные слоты или независимую квоту. При известной общей квоте нескольких аккаунтов учитывается и эта группа.
- При исчерпании квоты подключение исключается из выбора до известного сброса либо контрольной проверки после задержки. Неизвестный остаток квоты не считается неограниченным.
- Фабрика выбирает совместимое доступное подключение и продолжает задачу новой попыткой. Причина переключения и выбранное подключение сохраняются в истории.
- Ошибка авторизации требует восстановления доступа. Она не маскируется под исчерпание квоты; использование другого аккаунта возможно только по настроенной политике.
- Когда весь пул недоступен, задача ждёт освобождения слота, сброса квоты или восстановления доступа. После восстановления доступности диспетчер возобновляет выбор автоматически.
- Отменённая задача не возобновляется после сброса квоты. Ограничения числа попыток, времени и бюджета предотвращают бесконечные переключения.
- Переход на платный API по умолчанию выключен. Он разрешён только явно заданной политикой с денежным бюджетом. Само исчерпание пула такой переход не разрешает. Явно назначенный API-агент работает по собственным разрешениям и бюджету.

Для nocode-x адаптер проекта должен соблюдать инструкции репозитория: модульные Docker-проверки, ограничения широких прогонов и правила приёмки страниц.

**Критерии готовности:** две организации одновременно работают с разными проектами без смешения файлов, секретов и результатов. Роли и API-токены не позволяют выйти за разрешённую область. Проверены ограничения общего аккаунта в нескольких пулах, автосмена аккаунта и движка, ожидание полного исчерпания пула и возобновление после сброса квоты. Платный API не используется автоматически без явного разрешения и бюджета. Подключения GitHub, GitLab, корпоративных серверов и локального Git проходят общий процесс приёмки с учётом доступности PR/MR.

## Этап 6. Расширить интерфейс и API для повседневной работы

### Директор фабрики

Справа расположен диалог управления всей фабрикой или выбранным проектом. Директор работает через подключённые Codex CLI и Claude CLI, учитывает доступные подписки и права пользователя. Через диалог доступны создание организаций и проектов, управление пулами, профилями агентов, скиллами и MCP, постановка и координация задач, настройки и диагностика. Те же диалоги доступны из терминала через `darkfactory director`.

Каждое действие проходит обычный API с правами текущего пользователя. История приватна для его токена. Credentials, пароли и коды входа не передаются модели; директор направляет пользователя в форму авторизации. Очередь и результаты действий сохраняются. После перезапуска неопределённые действия не выполняются повторно без проверки. Платный API не включается автоматически.

### Связь с человеком

Настраиваемые каналы организации или проекта: Rocket.Chat через webhook и Telegram через bot token и chat ID. Вопросы, остановки, ошибки, лимиты и результаты отправляются по выбранным событиям. Доставка идёт через отдельную очередь с ограниченными повторами и скрытыми секретами. Задача может запросить уведомление через API; входящие команды мессенджеров не входят в первую версию.

### Экраны и настройки

Минимальный интерфейс включает:

- Организации и проекты.
- Участники, роли, права проектов и управление ограниченными API-токенами.
- Подключения и их состояние.
- Репозитории, адреса Git-серверов, авторизация и настройки веток.
- Пулы подписок, порядок выбора, занятость аккаунтов, доступные сведения о квоте и причины переключений.
- Задачи, этапы, логи и артефакты.
- Связи задач, родительские задачи, подзадачи и причины блокировки зависимостей.
- Ответы на вопросы агента.
- Отмену, повтор запуска и просмотр PR/MR либо внутренней записи изменения.
- Обязательные проверки, состояние интеграции в `preprod` и причины запрета автослияния.
- Активное время, циклы исправления, пределы параллельности и ожидание решения человека.
- Инциденты `preprod`, ход исправления и заблокированные слияния и зависимости.

Интерфейс и API позволяют вручную создать задачу, прочитать её состояние и артефакты, ответить на запрос уточнения, отменить или повторно запустить работу в пределах прав пользователя. Оба способа доступны в первой версии. Автоматический импорт обращений из внешних систем не обязателен для пилота и подключается отдельно.

Оба входящих потока создают задачи общего конвейера:

```text
Сообщение пользователя об ошибке
→ воспроизведение
→ критерии готовности
→ общий конвейер разработки и проверки

Задача владельца
→ уточнение и план
→ критерии готовности
→ общий конвейер разработки и проверки
```

**Критерии готовности:** фабрикой можно пользоваться через интерфейс и API без ручного редактирования базы данных и запуска команд на сервере. Оба входа создают задачи общего конвейера и соблюдают одинаковые права, ограничения и правила приёмки.

## Проверка первой версии

Провести пилот на nocode-x и втором репозитории. Начальный набор — десять багов и три небольшие фичи.

**Проходной порог: все 13 из 13 задач доведены до проверенного слияния в `preprod` без ручной правки кода, и все системные сценарии ниже пройдены.** Для пилотных проектов обязательные проверки настроены заранее. Задача, остановленная по лимиту или оставшаяся на ручной приёмке, не считается успешно пройденной. Уточнения требований у человека допускаются и учитываются в метриках вмешательств.

Дополнительно проверить:

- Перезапуск фабрики во время выполнения.
- Сбой и отмену исполнителя.
- Потерю авторизации и исчерпание квоты.
- Автоматическую смену подписочного подключения с сохранением незавершённой работы.
- Автоматический переход Codex ↔ Claude, сохранение артефактов, времени и циклов исправления.
- Полное исчерпание пула, автоматическое возобновление и запрет возобновления отменённой задачи.
- Конкуренцию проектов и пулов за один аккаунт, перезапуск во время переключения и соблюдение лимита попыток.
- Цепочку и разветвление зависимостей, отклонение циклов, блокировку при сбое предшественника и приёмку родителя по подзадачам.
- Повторную оценку зависимых задач после изменения принятого коммита и связи между проектами с проверкой прав.
- Возврат задачи после проваленной проверки.
- Изменение коммита после успешного ревью.
- Изоляцию двух организаций.
- Постановку и управление задачами через интерфейс и API; роли, ограничения токенов и изменение прав пользователя.
- Работающий процесс для GitHub, GitLab, корпоративных установок, обычного удалённого Git и локального репозитория; наличие PR/MR либо внутренних доказательств в зависимости от возможностей подключения.
- Изоляцию контейнеров, отсутствие доступа к хосту и production-секретам, ограниченный доступ координатора к локальным репозиториям.
- Запрет автослияния без обязательных проверок проекта; обязательное отдельное ревью, в том числе при совпадении движка с автором.
- Проверки результата объединения с актуальной `preprod`, конкурирующие изменения её вершины и отсутствие повторного слияния после сбоя.
- Самостоятельное исправление поломки `preprod`, приоритет исправления, блокировку остальных слияний и затронутых зависимостей, возобновление после проверенного восстановления.
- Исчерпание трёх циклов исправления и активного времени, сохранение счётчиков при повторном сбое того же исправления и ожидание решения человека без автоматического перезапуска.
- Общий предел двух активных задач, 60 минут активной работы на задачу и исключение времени ожидания из этого счётчика.
- Запрет автоматического платного API без явного разрешения и денежного бюджета; отдельный запуск явно назначенного API-агента.
- Отсутствие автоматического переноса в основную ветку и автоматического развёртывания приложения.

Оценивать долю принятых изменений, количество вмешательств человека, регрессии и затраты на принятую задачу. Для подписочных подключений отдельно учитывать занятость и доступные сведения об использовании квоты; не выдавать оценочную API-стоимость за фактический расход подписки.

## Граница первой версии

В первую версию входят три исполнительных адаптера; приватное размещение; интерфейс и API; несколько проектов и изоляция организаций; роли и ограниченные API-токены; контейнеры с тестовыми доступами; локальные и удалённые Git-репозитории, включая GitHub, GitLab и корпоративные серверы; PR/MR либо внутренние записи изменений; устойчивый конвейер до проверенного автослияния в `preprod`; обязательные проверки и отдельное ревью; связи и зависимости задач; пулы подписок с автоматической сменой аккаунтов и Codex ↔ Claude; ограниченное самостоятельное исправление `preprod`; сохраняемые пределы времени, исправлений и параллельности. При отсутствии обязательных проверок автослияние запрещено.

После подтверждения работоспособности рассматриваются:

- Автоматическое развёртывание тестового стенда из `preprod`.
- Автоматический перенос изменений в основную ветку.
- Автоматическое развёртывание в production.
- Публичный SaaS.
- Биллинг организаций.
- Marketplace агентов.
- Дополнительные интеграции и сложная аналитика.

**Первый рабочий срез — этапы 1–3:** три исполнительных адаптера в контейнерах; минимальная постановка задач через интерфейс и API; одна задача от запроса до проверенного слияния в `preprod`; внешний PR/MR и внутренний процесс обычного Git; смена двух подписочных подключений при исчерпании квоты и передача Codex ↔ Claude; цепочка зависимых задач; запрет автослияния без проверок и ограниченное исправление `preprod`. Начать последовательно, затем проверить общий предел двух активных задач на этапе 4. Полные настройки пулов, подключений и прав для нескольких организаций и проектов доводятся на этапе 5; полный интерфейс и API — на этапе 6.

## Браузерные проверки интерфейсов

Для UI-проектов исполнитель должен уметь открыть приложение в Chromium внутри своего контейнера, исследовать страницу через готовый MCP и запускать Playwright Test. В каталоге доступны готовые `browser-testing` и `project-browser`; владелец назначает их разработчику через списки. Планировщик и ревьюер сохраняют ограничения на запись.

Приёмка UI-изменения включает desktop 1440×1000, mobile 390×844, успешное действие, некорректный и пустой ввод, повторное действие, отсутствие горизонтального переполнения и ошибок браузера. Конкретные обязательные команды задаются проекту и выполняются также на результате объединения с актуальной preprod. При падении команды автослияние запрещено.

Артефакты браузера сохраняются отдельно для каждого запуска: скриншоты, trace и результаты тестов. Они доступны через карточку задачи и API с теми же правами проекта. Просмотр не исполняет HTML агента; чтение ограничивает размер и исключает переход по symlink. Артефакт дополняет проверки, но не заменяет их и не считается доверенным утверждением агента.

Дополнительный локальный пилот: исходная форма воспроизводимо проваливает проверки; настоящий Codex исправляет её, отдельная сессия делает ревью, preprod проходит повторный запуск независимого браузерного набора. Основная ветка и исходные тесты остаются неизменными. Тестовый двойник модели не доказывает эту приёмку.
